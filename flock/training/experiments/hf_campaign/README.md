# Standalone HF campaign

This experiment uses Transformers OLMo 2, Datasets and Accelerate independently of the shared trainer. The selected full architecture is freshly initialized OLMo 2 1B: 1,484,916,736 parameters including both untied matrices. The CPU harness accepts only tiny synthetic models. The full architecture is instantiated on the meta device in tests. A one-GPU path trains the 76M and 190M proxy presets on provisional mixes (below); nothing larger runs here.

From the flock checkout, create an isolated environment from the existing lockfile:

```sh
uv sync --all-extras --all-packages --dev --no-group gpu --group cpu-tests --frozen
CUDA_VISIBLE_DEVICES= RAYON_NUM_THREADS=4 OMP_NUM_THREADS=4 TOKENIZERS_PARALLELISM=false uv run --no-sync pytest -q tests/training/test_hf_campaign.py -n 0
```

The lock pins Transformers 5.20.1, Datasets 5.1.0, Accelerate 1.15.0 and torch 2.14.1. No shared environment or dependency file is changed. No model weights or remote dataset are downloaded by these tests.

## Input contract

Supply finite HF Dataset pools in immutable membership order, plus tokenizer, membership and exclusion fingerprints. Each admitted row supplies id, family_id, text, text_sha256, source_pin, split=train, admitted=true, rights_receipt and exclusion_receipt. Converted pools additionally require original_text, original_sha256 and conversion_receipt. The upstream producer must resolve source rights, reviewed conversion/protected spans, train-only eligibility, cross-script matching and canonical duplicate families. A receipt is a provenance reference, not an automatic legal or classification judgment.

The consumer rejects missing receipts, text/hash mismatches, duplicate families and configured held-out spans before encoding. A match rejects the whole document. The local forbidden-span hook is a synthetic exclusion oracle; it does not implement the full approved held-out normalization/matching pipeline. There is no production admission command. Long documents beyond the one-million-character/token fixture bound fail admission or stop; production segmentation and durable dedup indexes require the separate corpus gate.

Encode without automatic specials, then append one EOS per nonempty tokenization. Literal EOS tokens are retained. The initial stream token is context-only. Each next target has a stable pool/document/offset identity, including inserted EOS. A block contains aligned inputs and labels and carries its final token into the next block as context. Counts follow target source categories, separately tracking native/converted TC and EOS. Source categories do not assert actual token language. A pool switch can interrupt a long document at a block boundary; resuming its suffix later retains its original offsets and does not insert EOS. This explicit chunk-interleaving choice is not a claim of whole-document contiguous scheduling.

Explicit finite quotas control source allocation. Equal TC/EN allocations are supplied per optimizer update; source selection uses exact rational exposure ratios at block boundaries. There is no implicit repetition, source substitution or runtime shuffle buffer. The supplied immutable order is responsible for shuffling. Exhaustion stops. Source weights and repetition limits for real data remain unresolved. The in-memory duplicate-family ledger is intended for bounded synthetic fixtures, not a production-scale dedup index.

## Loss, restart and export

Both runtimes share one update loop. It requests HF logits without labels and computes external aligned summed CE divided by the update's total targets. This avoids HF's automatic label shift. Token-based warmup/cosine scheduling uses committed update-start targets. Updates cannot overshoot the declared endpoint. A terminal partial allocation preserves exact equal category totals.

Only completed optimizer updates replace the committed data snapshot. Prefetched producer positions are discarded before the next update. Accelerate checkpoints model, optimizer and RNG; a registered custom object saves committed pack buffers, membership positions, source/EOS counts, context and schedule counters. New checkpoint directories are checksummed and fsynced before atomic rename; an existing incomplete directory is a writer lock requiring inspection. Config/tokenizer/stream/schedule mismatch or corruption fails before resume. After a failed optimizer update, terminate the attempt and restore a previously committed checkpoint; the harness does not promise in-memory model rollback.

HF export saves model/config/tokenizer. Tests reload locally, compare the identical attention backend and execute a synthetic request through unchanged flock.eval ScoringModel. This verifies the adapter boundary, not parity or scores on frozen evaluation datasets. Full evaluation remains a separate process with approved instrument pins and settings.

## One GPU, provisional mixes

`python -m flock.training.experiments.hf_campaign.train` trains one proxy preset (`76m` or `190m`, the shapes and peak learning rates of `experiments/proxy/olmo2_proxy.py`, imported, not copied) on one GPU from a flock hub Lance mix pinned to a version:

```sh
uv run python -m flock.training.experiments.hf_campaign.train --size 190m \
    --dataset-uri s3://flock-datasets/corpora/provisional/mix-500m-tc25-seed0 --dataset-version 1 \
    --warmup-targets 190354176 --rows-per-update 128 --micro-rows 8 \
    --checkpoint-every 200 --output-dir /work/$USER/runs/proxy-190m-s0
```

The mixes written by `harvest mix` carry no admission receipts, so they never enter the admitted input contract above. `ProvisionalMix` is the only way in and the only input `GpuExperiment` takes. Every record of such a run (`run-*.json`, `summary-*.json`, the export's `experiment.json`) says `provisional: true`; `log.jsonl` sits beside them in the same run directory. The admitted path's checks are unchanged.

The mix is read in its stored order (it is already shuffled when written). Each document is encoded without specials and followed by one EOS, and the stream is cut into rows of 4096 targets plus one context token shared with the next row: concatenate-then-split without document masking, as OLMo 3 (sec. 3.6.3) and DataDecide pack. Every row is full, so no position is padding. Each document's token count is checked against the mix's `tokens` column (which counts the EOS, so every count is at least 1), and against `text_sha256` where a mix has one. The run's contract holds a digest of the tokenizer's encoding rules (the shared trainer's chunk fingerprint), so a resume with a tokenizer that assigns other ids fails, and the mix's S3 endpoint, absolute path and version number. A mix is named by its version number, never a tag: a tag can move or name another branch's snapshot. Item `u` of the mix is optimizer update `u`, so a run's position is its update count: spawned loader workers prefetch freely, and a resume restarts the sampler at the committed update. `log.jsonl` is appended by every attempt. Each line names its attempt (also the number of its `run-NNN.json` record) and the update its segment started from, so after a crash an update can appear twice. To rebuild the trained trajectory, read the attempts in order and, at each attempt's `resumed_at_update` (in its `run-NNN.json`), drop every earlier line past that update before adding the attempt's own lines; an attempt that logs nothing still drops them. A resume first cuts a partial last line left by a kill mid-write. Training rates come from the time between log lines of one segment, away from checkpoint saves; a summary's `started` and `finished` also span setup, saves and the export.

A row is 4096 targets, OLMo 2's context. `--rows-per-update` sets the batch; the OLMo ladder's 190M batch is 524,288 tokens (arXiv 2412.04403, Table 1), 128 rows here, and the 76M runs use half of it, 64 rows. `--micro-rows` sets how many rows go through the GPU at once, and the update accumulates their gradients. The loss is summed over targets and divided by the update's total, so accumulation gives the same gradient as one batch. The rate is set from the targets committed before each update, so the first update runs at a learning rate of 0. Warmup is linear over `--warmup-targets` (N targets, as the OLMo ladder warms up for N tokens), then cosine to 10 percent of the peak at the schedule's endpoint, one pass over the mix by default. `--max-updates` stops early without moving that endpoint. AdamW matches the flock Trainer's proxy recipe: betas (0.95, 0.99), weight decay 0.01 on every parameter, clipping at 1.0, no z-loss.

The model trains in BF16 autocast with FP32 weights and optimizer state, and the loss is computed on FP32 logits. Attention is PyTorch SDPA pinned to its flash kernel: packed rows need no mask, and the pin turns a silent fallback to a slower kernel into an error. The seed sets the initialization only; the data order is the mix's. The seed is part of the run's contract, so a resume must pass the same `--seed`. The micro-batch size sets the gradient's summation order, so it is part of the contract too. The launcher refuses to start unless Accelerate selected a CUDA device: without a GPU, or with `ACCELERATE_USE_CPU` set, it would otherwise train on the CPU. Accelerate's own gradient accumulation must stay at 1, since the loss is already divided by the update's targets.

Checkpoints and the export are written beside their final name with an `.incomplete` suffix and renamed when complete. A run directory has one writer at a time: nothing locks it, since `flock()` locks are not shared between nodes on the cluster's file system and a lock directory would outlive every crash. A resume refuses to start while any `.incomplete` file or directory is left, since a killed write needs inspection; a resume at the stop point finds the final checkpoint, export and summary already written and leaves them as they are.

To score an export, name it by its run and keep its directory where training wrote it: `flock eval run --model <run dir>/export-<update>@<first 40 hex of the contract in its experiment.json> --task fineweb_en --out <new directory>`. `flock.eval` takes a 40-hex revision as pinned without reading the files, and the contract names the recipe (model, optimizer, schedule, seed, mix and its version), not the weights: every export of one run shares it, so the export's own path, which carries its update, is what tells two exports apart, and a path must never be reused for other weights. The evaluation's `results.json` does not carry the export card's `provisional: true`, so keep the card with the results. This naming is for provisional runs only; before an admitted or reported run relies on a local export, `flock.eval` must identify it by a digest of its weights.

## Next gate

No production launcher, corpus materializer, distributed worker plan or FA3 dispatch is released here. Beyond one GPU at proxy size, these remain separate validation work: full-model memory, BF16/FA3 backward and causal checks, same-node throughput, distributed global-loss normalization, crash/durability tests on cluster storage and exact rank ownership. Pin the actual FA3 implementation and environment before GPU validation. Do not transplant historical throughput or budgets into this HF stack. The full 200B campaign needs its own data, metric, storage and compute release.
